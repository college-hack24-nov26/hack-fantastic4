# Android application

This directory contains the Kotlin and Jetpack Compose Vision prototype. It has splash, onboarding, permissions explanation, voice setup, home, assistant, and live rear-camera screens. The camera screen uses Google's pretrained EfficientDet-Lite0 INT8 for experimental COCO object guesses with boxes and scores. It provides no safety or navigation guidance. The production `LiveVisionEngine` carries camera detections to the overlay and short scene descriptions; the mock engine remains for tests.

The production assistant uses live camera observations and a no-op safety policy. The camera screen uses a foreground-only CameraX analysis adapter and MediaPipe Tasks Vision 0.10.32 on CPU. The old ONNX adapter remains in source for the private custom-model experiment but is never started in the normal camera loop. CAMERA is requested when the camera screen opens; RECORD_AUDIO is requested when listening starts. Voice commands use Android's on-device `SpeechRecognizer` only, with no online-recognizer fallback. Output uses installed Android TextToSpeech voices reported as not requiring a network connection.

The optional conversational path uses LiteRT-LM 0.18.0. No language model is bundled or downloaded by the app. To enable it, place the exact `Qwen3-0.6B.litertlm` artifact from `litert-community/Qwen3-0.6B` on the phone, open the assistant, and choose **Import Qwen3-0.6B model**. The app copies the selected file to temporary private storage, checks its SHA-256 (`c5f39b4191926786c3e6668b62af4d6eb15248dfc7a5348252a9b406f33f2108`), and installs it only if the checksum matches. Expect roughly 614 MB of model storage plus runtime cache and memory overhead. Deterministic commands and visual-safety refusals remain outside the LLM path.

On a Samsung SM-E546B running Android 16, the imported model loaded, a typed request generated a reply, and one spoken request was transcribed and routed to the model. The recognizer reported confidence `0.0` for that usable transcript, so Vision does not reject a request solely for that score. The assistant provides typed input when speech recognition fails, and diagnostic logs record recognition stages and error codes without recording audio or transcript text. Recognition reliability, Hinglish recognition and pronunciation, response latency, and longer conversations still need device evaluation. The model has no camera input; its replies must not be used for navigation, obstacle detection, or safety decisions.

## Experimental camera detector

The active camera model is Google's pretrained EfficientDet-Lite0 INT8, documented in the [MediaPipe model list](https://developers.google.com/edge/mediapipe/solutions/vision/object_detector). Download source: `https://storage.googleapis.com/mediapipe-models/object_detector/efficientdet_lite0/int8/latest/efficientdet_lite0.tflite`. The verified file is 4,602,795 bytes with SHA-256 `0720BF247BD76E6594EA28FA9C6F7C5242BE774818997DBBEFFC4DA460C723BB`. It uses the standard COCO 80 object categories (the metadata label map can contain unused placeholder entries). The corresponding TensorFlow EfficientDet [model listing](https://www.kaggle.com/models/tensorflow/efficientdet/tfLite) states Apache 2.0; confirm the exact Google-hosted binary's redistribution terms before publicly shipping the weight. The model is ignored by Git. Run `powershell -File .\scripts\get-efficientdet-lite0.ps1` before building to download, verify, and package it at `app/src/main/assets/detector/efficientdet_lite0_int8.tflite`. A build without the asset succeeds but shows a model-missing state at runtime. No model is downloaded by the app.

The detector uses one CameraX Preview and one `KEEP_ONLY_LATEST` ImageAnalysis use case. It rotates the viewport-cropped RGBA frame upright, bilinearly resizes to a 320×320 bitmap, and passes it to MediaPipe in synchronous IMAGE mode on one background worker. MediaPipe handles its own tensor conversion; Vision does not apply ONNX normalization. Model pixel boxes are normalized to the common CameraX viewport for the `FILL_CENTER` overlay. The default minimum score is 0.25 and can be adjusted on screen; scores are not calibrated safety probabilities. The initial cadence is 2 Hz and needs Samsung tuning. The diagnostics show conversion-plus-inference time, full frame time, result age, approximate camera drops, battery and Android thermal status. Thermal status is not a surface-temperature measurement. Frames are not stored by default.

The earlier private custom SSDLite detector displayed live boxes and labels, including false positives, and had held-out AP50 about 0.115. Those measurements do not apply to EfficientDet-Lite0. Neither model is suitable for safe-path, crossing, distance, obstacle-avoidance, or navigation claims. Detections never enter the safety policy. Hackathon eligibility of pretrained weights must be checked against the event rules; this model is not scratch-trained.

### Samsung live-camera validation (2026-11-04)

On Samsung SM-E546B (Android 16), the rear preview stayed responsive while CameraX frames reached MediaPipe and real model results appeared in Compose through `LiveVisionEngine`. The camera was aimed mostly at red fabric and the edge of another device. The detector repeatedly labeled the fabric `bed` or `umbrella`, which are false positives; occasional `cell phone` and low-score `chair` labels appeared near the device edge, but their physical correctness is unconfirmed. Person, bottle, and a clearly framed chair have not been tested in the live camera. The labels and rectangles remain explicitly experimental.

The common CameraX viewport crop is rotated upright and normalized for the `FILL_CENTER` overlay. Unit tests cover all four right-angle rotations and normalization. Portrait and forced-landscape previews rendered, and monitoring resumed automatically after rotation in both directions. Exact box position and size against a clearly identified object remain unverified. Airplane-mode testing showed live camera results continuing, and connectivity was restored. Stop cleared the overlay and released the detector session; restart loaded a new session. Automatic object announcements remained off; their cooldown and suppression behavior is covered by JVM tests, but audible output during live detection was not tested. No route or safety advice was enabled.

On a run with Qwen still installed and the phone charging with battery saver enabled, periodic camera-log samples had median conversion-plus-inference time 281.8 ms and P95 307.8 ms (29 samples); observed analysis cadence was about 1.9 Hz. These are sampled processing times, not end-to-end response latency or a performance guarantee. Device PSS was about 1.25 GB with the imported Qwen model present. After sustained use, Android reported thermal status 2; Vision marked monitoring degraded and hid results until recovery. The camera preview remained active, and stopping monitoring released the detector. No private camera frames were saved.

## Experimental camera descriptions

The camera and assistant can run on the same screen. A bounded in-memory scene store retains only recent COCO detector candidates, not images or video. A spoken or typed visual question is answered by deterministic wording before Qwen. Candidates require a raw score of at least 0.50 and a class-aware box match in two of the last three processed frames. Results expire after 1.5 seconds and are cleared on camera stop, failure, or restart. These are demonstration heuristics, not validated confidence or safety thresholds. Questions about safe routes, crossings, colors, text, distance, or motion receive explicit limitations.

Automatic object announcements are persisted in DataStore and off by default. When enabled, stable fresh candidate changes may be spoken with an eight-second minimum cooldown. The existing assistant owns the single TTS output; user requests preempt automatic speech, and obsolete automatic announcements are dropped. Qwen remains available for general conversation but receives no camera image or detector summary. Descriptions and announcements are experimental guesses, never mobility guidance.

## Voice-controlled camera prototype

The voice session is shared across the assistant and camera screens so navigation does not replace the recognizer, Qwen conversation, or TTS. One-shot on-device recognition routes start/stop camera, automatic-announcement on/off, camera status, visual questions, repeat, and stop-speaking commands before Qwen. A camera-start confirmation is spoken only after CameraX reports an active preview; a failure or timeout is reported instead. Camera stop invalidates the current scene. The camera analyzer continues on its own worker during voice interaction.

The accessible **Start listening** button begins each recognition request. Android's on-device `SpeechRecognizer` is not treated as an always-on wake-word service. Vision does not listen with the screen locked or in the background, and it does not silently fall back to a cloud recognizer. A dedicated offline wake-word engine would require separate model, battery, privacy, and device testing.

## Build setup

Open this directory as an Android Studio project or run `gradlew.bat :app:assembleDebug` on Windows. The project uses Android Gradle Plugin 9.0.1, Gradle 9.1.0, Kotlin 2.4.21, compile SDK 36, and Java 17 bytecode. The AGP 9 built-in Kotlin and new DSL are temporarily disabled because LiteRT-LM 0.18.0 was compiled with Kotlin 2.4 metadata. An Android SDK with platform 36 and a Java runtime supported by Gradle 9.1 are required. Set `ANDROID_HOME` or use an untracked `local.properties` to point to the SDK.

Inclusive Sans is not bundled because no font file was supplied. The app currently uses a system sans-serif fallback. The UI reference PNG files remain outside the repository in the laptop's `UI_Images` folder.
